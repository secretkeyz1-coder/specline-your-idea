# UI Reference template gallery

> **Implementation note; status reviewed 2026-10-03.** Recorded context, not fresh tests or a fixed inventory guarantee; the scanned source folder can change. [Navigation](README.md).

UI Reference offers three drawing methods: **Draw sendiri** (requirements/design system without a template), **Draw with template** (built-in gallery), and **Draw with your own template** (paste/upload HTML). This selects the layout source; screen planning and drawing keep their existing workflow.

The published gallery has 20 curated entry pages across Dashboard, Workspace, Login, Landing page and Store. Its source is `Referensi UI/`. The gallery scans that folder whenever opened or refreshed: added/changed/removed HTML is reflected without source edits or rebuilding. Known entries retain curated names and order; additional pages have deterministic path-based IDs and inferred categories (including Other). Common component/blank/error demos and asset directories are excluded. Category inference is a hint, not a guarantee of screen suitability. Search/category filters, selection, larger preview and analysed-layout confirmation are available. The existing reference can also be changed per screen. A changed reference marks already drawn screens out of date rather than silently overwriting them.

Templates guide composition, not requirement scope: all product screens, role permissions, workflows and states still come from the approved source. Auth/standalone screens retain their shell exception. New selections default to **Adapt template appearance**: sanitized HTML hierarchy and an imported visual system (colours, typography, density, radius and depth) accompany planning, drawing and element edits. **Layout only** retains the project Design System and the earlier brief-only behaviour. Existing references without a mode retain layout-only behaviour. Adaptation activates styled rendering, without rewriting the approved project Design System. Screen-specific templates override the global template. Example copy/data from the original template are not product requirements. Custom HTML still goes through the existing untrusted-layout sanitizer; built-ins use that same API. Large trusted built-ins first discard demo scripts/comments and SVG paths so those payloads cannot cut off the page's main content.

Built-in adaptation reads local stylesheets within the collection's realpath boundary and retains embedded CSS. Theme/body rules take priority in the bounded CSS evidence; the visual importer separates explanatory prose from CSS and resolves the final body font rather than framework reset defaults. Uploaded/pasted HTML must embed its CSS: remote stylesheets are not fetched and missing evidence is reported in the analysed reference. The result translates template structure into safe platform components; it does not execute vendor JavaScript or promise a pixel-identical copy. Rendering, comments, edits, exports and approval checks use the same effective per-screen visual tokens.

The stored adaptation includes sanitized hierarchy (40k characters maximum), visual CSS evidence (20k maximum), the derived system and limitations. CSS evidence is prompt data, never executed or injected into a preview. Changing a template invalidates the drawing digest. A redraw with a changed reference starts a new composition instead of sending the old HTML with an instruction to preserve its geometry. Planning notes remain functional hints when a later template replaces the earlier visual recipe. Task decomposition and the master build work order describe global/per-screen template appearances and explicitly give them precedence over the base project's palette; builders read the effective tokens from exported UI Reference HTML while retaining the approved component library.

Adaptation does not automatically approve UI Reference. The draft still needs content review and render checks. The real FiberStock test caught generated technical copy on login, missing role-edit affordances and low-contrast custom status labels; these were corrected in the test project. Those corrections do not imply the AI will always produce a complete screen without review. A requested font stack is preserved in the tokens; if its font asset is unavailable in the safe preview, the browser uses its fallback family.

Previews are optional PNG screenshots of script-free reference pages at 1440×900; template JavaScript is never served into the application. Screenshot generation also disables browser JavaScript, rejects non-visual files and applies a no-script CSP. Vendor charts, menus and other script-generated demo content are not live; pixel parity with runnable originals is not guaranteed. Six CDN-Tailwind pages have statically compiled CSS so their styling does not require executing the CDN script. New pages without screenshots show an explicit placeholder and remain selectable for analysis. If HTML has a newer modification time than its screenshot, the gallery treats the preview as outdated until regenerated. Scrapers must not preserve old HTML timestamps if relying on that freshness check. Preview endpoints expose catalog IDs only. HTML reads also use catalog IDs and enforce a realpath boundary. Project access, write scope and AI rate limiting remain enforced by the existing analysis API.

`Referensi UI/LICENSES` and original source notices remain in the collection. The web Docker image includes the collection; API/agent images do not need it. For ongoing scraping in production, bind-mount the host collection into the web container (or set `UI_TEMPLATE_DIR` to a mounted directory); an image-baked copy only changes when the image is rebuilt. Preview generation may need internet for templates that depend on CDN assets. The application itself displays stored screenshots.

```powershell
bun apps/web/scripts/ui-template-previews.ts # only pages without a preview
# Refresh only a changed entry:
bun apps/web/scripts/ui-template-previews.ts material-kit
bun test apps/web/tests/ui-templates.unit.test.ts apps/api/tests/ux-layout.unit.test.ts
bun run --filter '@sdd/web' typecheck
bun run --filter '@sdd/web' build
```

The complete vendor sources/build tooling belong in a verified owner-local archive outside this repository, not `Referensi UI/`. The 2026-10-04 separation preserves 6,099 original files in `../SPECLINE VENDOR ARCHIVE cb049a4/`; `asset-inventory.json` records distributed bytes, source hashes, external URLs and existing unresolved links. Rebuild into a fresh directory with `bun apps/web/scripts/curate-ui-references.ts <verified-archive> <new-output>`, review/test it, then replace the published bundle. Never run vendor installs as part of publication. See [collection README](../Referensi%20UI/README.md) for archive hashes and restoration. Docker allowlists visual files/notices; the build stage does not consume the reference library.

To add a choice: archive and review the full HTML/assets/licenses outside the repository, curate script-free visual assets into `Referensi UI/<source>/`, then reopen or refresh the gallery. Prefer writing to a temporary file and renaming to `.html` when complete, so partially written pages are not offered. Generate missing previews when convenient. For manually curated naming/order, add an optional entry to `apps/web/src/lib/ui-templates.ts`. No project database migration is needed.

Validation on 2026-10-03: 16 tests passed (197 assertions), web typecheck zero errors/warnings, production build passed. Browser smoke tests verified all three methods, category filtering, built-in analysis requests, custom HTML file upload, apply/reset, refresh showing new entries, 390px layout and no browser errors. The browser test used a read-only API mirror with stub analysis replies and did not mutate the existing FiberStock project; it does not substitute for the separate requested real-provider FiberStock template run.
